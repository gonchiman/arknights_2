# 共通ルールの運用

作業開始時に読む。共通ルールは専用の `project-rules` リポジトリを原本とし、このプロジェクトには版を固定したコピーを保存する。普段の作業では、このリポジトリ内の指示だけを読めばよく、原本リポジトリやネットワークへの接続は不要。

## 管理するファイル

- `instructions/shared/` は同期ツールが管理する共通ルールのコピー。個々のファイルをこのプロジェクトで直接変更しない。
- `project-rules.lock.json` は取り込んだ原本の版と、同期対象の整合性を確認する情報を管理する。共通ルールの更新時は同期ツールで更新し、本文のコピーと一緒にGit管理する。
- `scripts/sync-project-rules.mjs` は、検査・差分確認・同期を行う共通のCLI。これも原本から同期し、プロジェクトごとに別の実装へ書き換えない。
- このプロジェクトだけの条件、例外、実装や見本への参照は、`instructions/` の各入口ファイルや用途別の `docs/` へ追記する。共通本体を複製して個別修正しない。

## 検査

プロジェクトルートで次を実行する。原本のクローンや通信は不要で、保存済みのコピーとロック情報を検査する。

```sh
npm run rules:check
```

検査に失敗した場合は、ローカル変更や同期漏れを確認する。本文をロック情報に合わせて手作業で書き換えたり、ハッシュだけを更新して一致させたりしない。

## 差分確認と更新

共通ルールを変更する場合は、原本の対象ファイルを修正・検証してコミットしてから、このプロジェクトで差分を確認・同期する。未コミットの同期対象からは取り込まない。以下は両リポジトリを同じ親フォルダーに置いた場合の例であり、実際の配置に合わせて `--source` を指定する。

```sh
npm run rules:diff -- --source ../project-rules
npm run rules:sync -- --source ../project-rules
npm run rules:check
```

- `diff` は原本との変更内容を確認し、`sync` は同期対象のコピー・CLI・ロック情報を更新する。更新後は本文とロック情報、プロジェクト固有の追記との整合性を確認する。
- 共通に適用したい変更は原本側へ、アークナイツだけの条件はローカルの追記へ保存する。個別の条件を共通本体へ混ぜない。
- 各プロジェクトはロック情報で取り込む版を固定する。原本が更新されても、このプロジェクトのコピーは自動では変わらない。
- 同期中の `project-rules.sync.lock` は二重実行の防止と復元記録に使う。処理が止まって残った場合は所有プロセスと復元記録を確認し、無条件に削除しない。
- 別PCでこのプロジェクトを使うだけなら原本のクローンは不要。共通ルールを更新する場合は原本リポジトリもクローンし、上記の差分確認・同期を行う。原本の場所を個人フォルダーの絶対パスに固定しない。
- このプロジェクトの同期を、ほかのプロジェクトへも更新を適用する指示として扱わない。ほかのリポジトリの更新は、その更新も依頼された範囲で個別に行う。

## 更新時の確認

共通本文と各入口ファイルの適用条件、例外、参照先が一致していることを確認する。既存の実装・見本・仕様を一括変更せず、ルールの更新とアプリ機能への適用を区別する。
